# BRAIN Diet — start here

Permanent orientation for Codex/Cursor sessions. This is a navigation instruction, not scientific authority or permission to change the project.

**Session task:** `<paste the specific user task, scope, exclusions and publication permissions here>`

1. Confirm the repository root, current directory, branch, HEAD, worktree and Git status (`git rev-parse --show-toplevel`, `git branch --show-current`, `git rev-parse --short HEAD`, `git worktree list`, `git status --short`, `git remote -v`). Do not assume `origin` is GitHub. Inspect tracked and untracked changes before editing.
2. Read [AGENTS.md](../AGENTS.md), including presentation approval and concurrent-work rules.
3. Read [PROJECT-CONTEXT.md](PROJECT-CONTEXT.md) for a short architecture and scientific-distinction overview.
4. Use [system/INDEX.md](../system/INDEX.md) to select the authoritative contracts relevant to the task. Orientation does not require reading every Stage 2A/2B line; scientific implementation requires reading the applicable rules in full, including dated amendments.
5. For scientific or presentation tasks, locate the relevant approved canonical PM example and template before proposing new structures. Reuse existing components and conventions rather than creating parallel implementations.
6. Read [DECISIONS.md](DECISIONS.md) and the relevant [workstream handoff](handoffs/INDEX.md). Confirm authority and scope from linked source records, not from a summary alone.
7. Inspect the relevant existing manifests, dated review entries and recent Git history. Use [review/INDEX.md](../review/INDEX.md). Check actual canonical records when statuses disagree. A queue field or old report is not proof of current completion.
8. Distinguish **approved** (author decision and scope), **proposed** (not activated), **implemented** (code/data present), **validated** (named checks passed), **pending** (unfinished or blocked) and **published** (verified release). These states are independent; a commit is not scientific acceptance or a deployment.
9. Preserve uncommitted and concurrent work. Do not reset, stash, stage unrelated drafts, regenerate approval baselines, or infer branch incorporation from filenames. Follow the current task's Git/publication boundaries.
10. Before modifying files, briefly report the task as understood, checkout, relevant authority, known blockers and intended scope. This is an orientation update, not an automatic approval checkpoint for already authorised work.
11. If no specific task was supplied, stop after orientation and wait for one. Never start Gold Standard PM development, Stage 2C activation or contract refactoring from this hub alone.

After meaningful work, update the relevant workstream handoff or manifest. Record the decision, scientific rationale, files changed, validation results, branch/commit and remaining work. Distinguish local-only changes from committed or published changes. Preserve historical decisions; avoid copying whole contracts into summaries. Current explicit author instructions and canonical scientific records/contracts take precedence over these orientation files. Flag unresolved authority conflicts.
